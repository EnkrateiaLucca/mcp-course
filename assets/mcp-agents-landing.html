CHAPTER 01

A model on its own can only talk

An LLM turns text into more text. It knows what it saw during training, and nothing after that.

It can't read your files, check the news or press a button. Ask it to, and the best it can do is say so.

Key ideaText in, text out. Everything else has to be given to the model.
Ask the model each question and watch which ones it can answer.

CHAPTER 02

Tools and a loop make an agent

Give the model a list of tools: functions with a name, a description and typed inputs. The model can't run them. It can only ask.

Your code runs the tool and hands the result back. Then you call the model again. That repetition is the agent loop, and every agent framework is built on it.

Key ideaThe model decides. Your loop executes. The loop ends when the model stops asking for tools.
Press Step and follow the dot, the highlighted code line and the log together.

CHAPTER 03

Why a protocol? N × M becomes N + M

Tools written for one app don't work in another. Every app has to integrate every tool on its own terms.

MCP (Model Context Protocol) is a shared contract. A tool provider writes one server. Any app that speaks MCP can use it. It's the same move USB made for hardware.

Key ideaWrite the server once. Every MCP host can plug it in.
Add apps and tools with the sliders, then flip to “With MCP” and compare the count.

CHAPTER 04

Anatomy: host, client, server

The host is the app you use. It runs the model and the loop. For each server it connects to, it starts one client.

Each server is a small program that offers capabilities. The model sees one merged list of tools and never talks to a server directly.

Key ideaOne host, many clients, one client per server. The host stays in charge.
Click every box and the dashed wires to read what each part does.

CHAPTER 05

Three primitives, three owners

A server can offer three kinds of things. They differ by who decides when they're used.

Get this right and server design gets easy. Actions go in tools. Context goes in resources. Workflows a person starts go in prompts.

Key ideaTools → the model. Resources → the app. Prompts → the user.
Guess who controls each primitive before you read the answer.

CHAPTER 06

On the wire: just JSON-RPC

Client and server exchange small JSON messages. A request has an id and expects a reply. A notification has no id and expects nothing back.

First a handshake, then discovery, then calls. Every MCP connection follows these steps.

Key ideainitialize → tools/list → tools/call. Learn those three and you can read any MCP log.
Send messages one at a time, then click any arrow to inspect it.

CHAPTER 07

Never trust a tool description

The model reads the full tool description. The approval dialog shows you a summary. A malicious server can hide instructions in the gap. This is called tool poisoning.

The fix lives in the host. A PreToolUse hook checks every call before it runs, whatever the model was talked into.

Key ideaGuard actions, not words. Hooks see what the model is about to do.
Compare the two views, run with the hook off, then switch it on and run again.

CHAPTER 08

From your laptop to the internet

The messages stay the same. The transport carrying them changes.

stdio: the host starts the server as a subprocess on your machine. Streamable HTTP: the server runs anywhere, and every message is an HTTP POST, so you need auth.

Key ideaSame server code. Change one line to move it from local to remote.
Switch transports and compare the wiring and the config.

MCP course · Day 2 · Modules 04 & 05

Production shape & deploy: the presenter's one-pager

Built from presentation.html and demos/04, demos/05. Every command marked verified was run on this Mac on 2026-09-22.

Read this if nothing else

  • Production = the same research server plus four moves: intent-grouped tools, HTTP transport, an auth seam, and hooks/permissions/evals. Nothing about the use case changes.
  • Deploy = ship the MCP server, not the agent. app = mcp.streamable_http_app() is the whole web app. Uvicorn runs it on your laptop; Vercel imports the same object.
  • Two servers, two ports. Demo 04 on :8765, bearer token required. Demo 05 on :8000, open by default, stateless + plain JSON so it survives serverless.
  • Hosts differ in reach. Claude Code and the SDK can hit localhost and send headers. Claude web/desktop needs a public URL and speaks OAuth-or-nothing. That constraint decides the whole demo 05 flow.
  • Pre-flight three times: test_client.py against localhost, through the tunnel, and after Vercel. Quit Anki first: it owns port 8765 on this Mac. Present the agent from an empty CLAUDE_CONFIG_DIR so your global MCP servers stay out of the log.
Contents

1The mental model (for you first)

An MCP server over HTTP is a normal web server with one endpoint, /mcp. A client POSTs a JSON-RPC message, the server answers with a JSON-RPC message. Everything in modules 04 and 05 wraps that one fact.

uvicorn (local)  or  Vercel function (cloud)   ← something has to RUN the app
  └─ Starlette ASGI app = mcp.streamable_http_app()   ← the app. FastMCP builds it for you
       └─ BearerAuthMiddleware                         ← sees every request first (demo 04)
            └─ POST /mcp  (JSON-RPC)                   ← initialize, tools/list, tools/call…
                 └─ your @mcp.tool() functions         ← unchanged from module 01

The same Starlette ASGI app from mcp.streamable_http_app(). In demo 05 it is built at module level as app = build_app() so api/index.py can simply from server import app.

The auth seam, both halves

# server side (research_server.py)
app = mcp.streamable_http_app()          # the ASGI app
app.add_middleware(BearerAuthMiddleware) # the seam
uvicorn.run(app, host="127.0.0.1", port=8765)

# agent side (research_agent.py)
mcp_servers={"research": {
    "type": "http",
    "url": SERVER_URL,
    "headers": {"Authorization": f"Bearer {AUTH_TOKEN}"},
}}
Say it like this

The bouncer stands at the front door, not inside each room. Today the bouncer checks a password. Tomorrow it checks an OAuth badge. The rooms, meaning the tools, never change. That is the whole point of a seam.

The auth ladder has three rungs: nothing (demos), a static bearer token (this demo, rung 2), and OAuth 2.1 where your server is a resource server and clients register with Client ID Metadata Documents. Rung 3 is what "Add custom connector" in Claude speaks. Teaching it end to end is its own course. The lesson here is only that rung 2 → 3 touches one middleware and zero tools.

Control: four small pieces in research_agent.py

  • Allow-list: allowed_tools lists exactly the three mcp__research__* tools. MCP tools are never auto-approved by permission modes, so this is required, not optional.
  • can_use_tool: a callback that denies anything not in the allow-list. Defense in depth next to the allow-list.
  • PreToolUse hook: denies a topic under 3 characters and any brief_path containing .. or starting with /. Cheap validation before a network round-trip.
  • PostToolUse hook: one log line per tool call, reading the tool's ok field.

Telemetry is not evals

ExecutionTracker reads ResultMessage and prints status, duration, estimated cost, and tool counts. That tells you the agent ran. evals.py tells you it was right, in three layers:

  1. Deterministic grade_brief(): file exists, has a Sources section, has links, mentions the topic, is over 300 chars. Free.
  2. LLM-as-judge judge_brief(): the SDK itself, locked to the Read tool, scores faithfulness, coverage, usefulness from 1 to 5 and must answer in JSON.
  3. Gate run_evals(): runs three topics end to end, passes only if layer 1 passes and the worst judge score is at least 3, exits 1 otherwise. That exit code is what CI would key on.

structured_output_demo.py closes the other end: options.output_format = {"type": "json_schema", "schema": ResearchReport.model_json_schema()} makes the agent's final answer a validated Pydantic object instead of prose. A structured verdict is gradeable; a paragraph is not.

Tool search changed the why, not the what. Students who read older material will say "fewer tools saves context tokens." The SDK now defers tool definitions by default, so that argument is weaker. Intent-grouped tools still win because the agent makes fewer wrong-tool choices and fewer round-trips, and less intermediate data flows through context. You will see tool search live: the agent's first call in demo 04 is ToolSearch, loading the tool definition on demand.

Where exactly would OAuth replace the bearer check, and what else would change?

Only BearerAuthMiddleware on the server and the headers dict on the agent. The three tools, the hooks, and the evals are untouched.

Why does the allow-list need a can_use_tool callback next to it?

Defense in depth. The allow-list gates what the SDK offers; the callback is your code deciding at call time. If one is misconfigured the other still denies. The hook is a third layer that inspects the arguments.

What is the difference between what ExecutionTracker reports and what evals.py reports?

Tracker: status, duration, cost, tool counts, meaning "it ran". Evals: deterministic checks plus judge scores with an exit code, meaning "it was right".

A student's agent prints "MCP server 'research': failed". What are the two most likely causes?

Token mismatch between the two terminals, or the server is not running on 8765 (on this Mac, usually because Anki has the port).

4Module 05: what changes when you deploy

The reframe on the slide: not "wrap your agent in FastAPI", but "deploy the MCP server itself and let every host connect." One server serves Claude web, Claude Code, Cursor, and ChatGPT. That is module 01's M×N payoff over the public internet.

Why those three flags

mcp = FastMCP("research-explorer",
    stateless_http=True,   # any replica answers any request
    json_response=True,    # one JSON body, no SSE stream
    host="127.0.0.1", port=8000,
    transport_security=TransportSecuritySettings(
        enable_dns_rebinding_protection=False))  # else 421 behind tunnel/Vercel
  • Stateless: a serverless function may be a fresh process on every request. With sessions, request two would land on a process that never saw request one. Stateless means every request carries what it needs. The 2026-07-28 spec makes the protocol core work this way.
  • JSON response: serverless platforms buffer or time out long-lived streams. A plain JSON reply is boring and works everywhere.
  • Host check off: the SDK auto-enables DNS-rebinding protection when you bind 127.0.0.1 and rejects any non-localhost Host header with 421 Misdirected Request. A tunnel or Vercel hostname is exactly that. It looks like a Cloudflare error but it is your origin refusing. Verified: a request with Host: abc.trycloudflare.com gets 200 from this server.

The Vercel wrapper is three files

  • api/index.py: adds the parent dir to sys.path and does from server import app. Vercel's Python runtime looks for a variable named app there.
  • vercel.json: rewrites every path to /api/index, so /mcp reaches the app.
  • requirements.txt: mcp[cli]>=1.12,<2 and ddgs for Vercel's builder. Local runs use the inline UV metadata instead.

The MCP App is a tool plus a resource

@mcp.tool(meta={"ui": {"resourceUri": "ui://research-explorer/app.html"}})
def research_explorer(topic: str, max_sources: int = 6) -> dict: ...

@mcp.resource("ui://research-explorer/app.html",
              mime_type="text/html;profile=mcp-app")
def research_explorer_app() -> str:
    return APP_HTML_PATH.read_text()

The host reads the resource, renders the HTML in a sandboxed iframe, and talks to it over postMessage. app.html does the handshake in about 50 lines of vanilla JS so students see there is no magic:

DirectionMessageMeaning
View → Hostui/initialize (protocolVersion 2026-01-26)Hello, here is what I can display
View → Hostui/notifications/initializedReady
Host → Viewui/notifications/tool-inputThe arguments the tool was called with
Host → Viewui/notifications/tool-resultThe tool result; the view renders cards
View → Hosttools/callThe Search button re-runs the tool through the host

HostLocalhost URL?Custom headers?Renders MCP Apps?

This table is why demo 05 goes local → tunnel → connector → Vercel, and why MCP_AUTH_TOKEN stays unset for it.

Why does a tunnel produce a 421 on a default FastMCP server, and which line fixes it?

Binding 127.0.0.1 turns on DNS-rebinding protection, which only accepts localhost Host headers. The tunnel forwards its own hostname. transport_security=TransportSecuritySettings(enable_dns_rebinding_protection=False) turns the check off.

What two MCP primitives make an App, and what links them?

A tool and a resource. The tool's _meta.ui.resourceUri points at the resource's ui:// URI, which serves HTML with mime type text/html;profile=mcp-app.

Why can you not add demo 04's server as a Claude custom connector?

The connector UI has no field for a bearer header. It supports OAuth or no auth. Demo 04 requires a bearer token, so only Claude Code and the SDK can use it.

7Explaining it to students

One line each

  • Intent-grouped tools: give the agent a "make me a brief" button, not a toolbox.
  • streamable-http: the server is a URL now, not a subprocess on your laptop.
  • Auth seam: the bouncer is at the door, not in every room. Swap the bouncer, keep the rooms.
  • Hooks and permissions: checkpoints around every tool call, plus a guest list.
  • Telemetry vs evals: telemetry says it ran and what it cost. Evals say it was right.
  • Stateless: every request carries everything it needs, so any copy of the server can answer.
  • Tunnel: a temporary public door into your laptop.
  • MCP App: a tool that ships its own small web page; the chat renders it in a sandbox.

Questions they will ask

Why not just wrap the agent in FastAPI like every tutorial?

Then only your app can use those tools. Deploying the server lets every host connect: Claude, Claude Code, Cursor, ChatGPT. The archived demo did the FastAPI + SSE route in about ten times the code.

Is a bearer token secure enough for production?

Only over HTTPS, and it is one shared secret with no per-user identity or scopes. That is why it is rung 2. Production is OAuth 2.1 with the server as resource server. The wiring you saw is the same; the credential changes.

Where does OAuth actually go?

In place of BearerAuthMiddleware, typically an API gateway or an auth library that validates tokens. The tools do not change. Claude's connector flow expects it.

Why does demo 05 have no auth if this is the "production" module?

Claude's connector UI cannot send a bearer header, and the demo is about reachability and the App. Set MCP_AUTH_TOKEN and the optional middleware turns on for clients that can send headers. The real answer is OAuth, covered as the ladder.

What does the 2026-07-28 spec change here?

The protocol core becomes stateless: no initialize handshake, no Mcp-Session-Id. Demo 05 is already shaped that way with stateless_http=True. Do not bump to SDK v2 yet; it renames FastMCP to MCPServer.

Does the MCP App run on my server?

No. The server only serves the HTML as a resource. The host runs it in a sandboxed iframe and relays tools/call for it. The server never learns whether a UI was rendered.

9Recap

Production shape is four moves on the same server: intent-grouped tools, HTTP, an auth seam, control and evals. Deployment is shipping that server as an ASGI app, made stateless and JSON so it survives serverless, then letting hosts connect: Claude Code on localhost, Claude web through a tunnel or Vercel. The App is a tool plus a resource. Pre-flight three times and quit Anki.

Module 04: the agent goes to production

Same research assistant as 00–02. Four changes make it production-shaped: 3 tools instead of 7, HTTP instead of stdio, an auth seam, and hooks + evals. ~40 min.

Open with: "Everything you built so far runs as a subprocess on your laptop with no lock on the door. Today we move it to a URL and put a lock on it. Nothing about the tools changes."

1. Auth, explained so you can explain it

The only question auth answers

"Who is calling my server, and are they allowed?" On stdio that question never came up: the server was a child process of the client, so whoever ran the client owned the server. On HTTP anyone on the network can send a request. So now every request must carry proof.

The two halves (this is the whole demo)

research_agent.py research_server.py ───────────────── ────────────────── ClaudeAgentOptions(mcp_servers={ app = mcp.streamable_http_app() "research": { app.add_middleware(BearerAuthMiddleware) "type": "http", │ "url": ".../mcp", ▼ "headers": {"Authorization": every HTTP request ──► header == "Bearer <MCP_AUTH_TOKEN>" ? "Bearer <MCP_AUTH_TOKEN>"}}}) │ yes ──► MCP handles it (tools run) │ no ──► 401, MCP never sees it
  • Client half: the SDK attaches one HTTP header to every request it makes to that server. That is all the client does.
  • Server half: a Starlette middleware runs before the MCP layer parses anything. Wrong or missing header → 401. Tool code never knows auth exists.
  • The shared secret: both sides read MCP_AUTH_TOKEN from the environment. Same value in both terminals or you get 401.
Say: "Auth lives at the HTTP layer, not the MCP layer. MCP is just JSON-RPC over HTTP, so anything that protects HTTP protects MCP. That's why you'll never see the word auth inside a tool function."

The ladder: where a static token sits, and what OAuth changes

RungHow the client gets a tokenHow the server checks itUse when
0. None——stdio on your laptop
1. Static bearer (this demo)You paste it in an env varString compareInternal service, one trusted caller, dev/staging
2. OAuth 2.1 (the spec's answer)Host sends the user through a login flow, receives a short-lived scoped tokenVerifies signature or introspects with the auth server, checks scopesMany users, third-party hosts (Claude "custom connector"), per-user permissions

The insight that makes OAuth click: OAuth changes how the token is obtained and how it is verified. The transport is identical: still Authorization: Bearer ... on every request, still a middleware at the same seam. Swap rung 1 for rung 2 and no tool function changes.

OAuth vocabulary they'll hear: your MCP server is the resource server (it holds the tools). An authorization server issues tokens (Auth0, Okta, your own). The MCP host (Claude, Cursor) is the client that runs the login flow. Client ID Metadata Documents (CIMD) let a host identify itself to your auth server without pre-registration.

If someone asks "why not just do OAuth in the demo?": "It's 100+ lines of redirect handling that teaches OAuth, not MCP. The seam is the lesson. Module 05 shows what a host that speaks OAuth-or-nothing looks like from the outside."

2. Live run script

Terminal 1: server

cd demos/04-production-research-agent
export MCP_AUTH_TOKEN=demo-secret
uv run research_server.py          # http://127.0.0.1:8765/mcp

Point at the log line that prints the token. Point at SystemExit if the env var is missing: fail fast, never default to a secret.

Terminal 2: prove the lock with curl (do this before the agent)

BODY='{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'

# no header  →  401
curl -s -X POST http://127.0.0.1:8765/mcp \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -d "$BODY"

# right header  →  initialize result
curl -s -X POST http://127.0.0.1:8765/mcp \
  -H 'Authorization: Bearer demo-secret' \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -d "$BODY"

Server log shows rejected request: bad/missing Authorization header for the first and nothing for the second. That is the seam, visible.

Terminal 2: the agent

export ANTHROPIC_API_KEY=sk-...  MCP_AUTH_TOKEN=demo-secret
uv run research_agent.py "Research how MCP authentication works"

What to point at, in order:

  1. MCP server 'research': connected in the init log. A 401 shows up here as failed, not as "the agent ignored the tool" later.
  2. One tool call: mcp__research__research_topic. In module 01 this was 4–6 calls. Intent-grouped tools.
  3. tool ... -> ok: the PostToolUse hook logging.
  4. The summary box: status, duration, cost. Telemetry.

Optional: break it live

Change the token in terminal 2 only and rerun. Init log shows the server as failed and the agent answers without tools. Then ask: "Where in the code would you catch this in production?" Answer: the init status check.

5. Questions students ask

  • "Is a bearer token secure?" Over HTTPS, yes as a transport. The weakness is the lifecycle: it never expires, can't be scoped, and one leak means rotating everyone. OAuth fixes the lifecycle, not the transport.
  • "Where does the token go in Claude Desktop?" Nowhere. Custom connectors speak OAuth or no auth. A static bearer works for the SDK, Claude Code, and your own clients only.
  • "Why middleware and not a check inside each tool?" One place, runs for every request including initialize and tools/list, and the tool author can't forget it.
  • "Does the server know which user called?" Not at rung 1. That is exactly what OAuth adds: the token carries identity and scopes, and the middleware can put them on the request for tools to read.
  • "Can I use an API gateway instead?" Yes, and in production you usually do. The middleware is the same seam moved one hop out.
Close with: "Three tools, one URL, one header, two hooks, one eval file. That's the whole production shape. Module 05 puts it on a public URL."

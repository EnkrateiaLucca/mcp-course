Lesson 3: The agent service

Goal: you can turn research_agent.py (a CLI script) into a containerized HTTP service that streams turns, resumes conversations after a restart, and connects to your MCP server with a locked-down configuration.

TL;DR

The problem: Today the agent is a script you run by hand. It forgets everything when it stops, and it can use any tool it finds lying around.

The shape of the solution:

  • Give it a front desk: wrap the agent in a small web service. Users send a message to a conversation ID and get the reply streamed back.
  • Take away what it doesn't need: no shell, no file access, only your MCP tools. Add a turn limit and a spending limit.
  • Give it a memory that survives restarts: store its notes on a mounted drive or in a database, so the conversation picks up where it left off.
  • Pack it in a box: one Docker image that runs the same on your laptop and in the cloud.

Think of it like: Turning a freelancer you phone directly into an employee at a reception desk, with a locked toolbox, a notebook kept in the office, and an expense limit.

1. The interface contract

The hosting cookbook defines one contract and keeps it the same across Docker, Modal and Kubernetes. Only the machinery around the container changes. Adopt it as-is:

GET  /health                          → 200 {"status": "ok"}     (no auth: orchestrators probe it)

POST /sessions/{session_id}/messages  body: {"prompt": "..."}
     → 200 text/event-stream
       event: message   data = one serialized SDK message (System / Assistant / Result)
       event: done      turn complete
       event: error     data = {"message": "..."}
     Creates the session on first use, resumes it after that.
     The stream carries only the new turn, not the history.

session_id must match ^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$   (else 400)
Port 8000. Required env: ANTHROPIC_API_KEY. Persist CLAUDE_CONFIG_DIR (/data).
The cookbook's own warning: this server has no user authentication. It must sit behind a gateway that (1) authenticates callers and (2) forwards only the session_id values that belong to the caller. Never expose port 8000 to the internet. The hosting docs say the same thing: the agent receives pre-authenticated requests and does not validate user tokens.

2. Lock down the options

This function replaces build_options() in module 04. Every line answers a production concern.

def build_options(*, tenant: str, mcp_token: str, resume: str | None) -> ClaudeAgentOptions:
    return ClaudeAgentOptions(
        model=os.environ.get("MODEL", "claude-sonnet-5"),
        system_prompt=SYSTEM_PROMPT,

        # Tools: ONLY our MCP server. No Bash, Read or Write inside the container.
        tools=[],                                   # removes every built-in tool
        mcp_servers={"research": {
            "type": "http",
            "url": os.environ["RESEARCH_MCP_URL"],  # internal URL in production
            "headers": {"Authorization": f"Bearer {mcp_token}"},   # per user (section 3)
        }},
        strict_mcp_config=True,                     # ignore any .mcp.json or plugin servers on disk
        allowed_tools=["mcp__research__*"],         # MCP tools are not auto-approved otherwise

        # Isolation: nothing from the filesystem leaks into the prompt
        setting_sources=[],                         # no settings files, no CLAUDE.md
        cwd=f"/data/work/{tenant}",                 # stable per tenant: resume depends on it
        env={
            "CLAUDE_CONFIG_DIR": f"/data/config/{tenant}",
            "CLAUDE_CODE_DISABLE_AUTO_MEMORY": "1", # auto memory ignores setting_sources
        },

        # Runaway guards: a session has no timeout of its own
        max_turns=12,
        max_budget_usd=float(os.environ.get("MAX_BUDGET_USD", "0.50")),

        resume=resume,
    )

3. Per-user MCP credentials come for free

You build ClaudeAgentOptions on every request. So the MCP headers can differ on every request. That is the bridge between lesson 2's OAuth server and a real user:

  1. The gateway authenticates Alice and forwards two trusted headers: X-Tenant: alice and a token whose audience is your MCP server (for example from an OAuth token exchange).
  2. The agent service puts that token in mcp_servers["research"]["headers"].
  3. The MCP server verifies it and scopes every tool to alice.

At rung 1 (one service token), read mcp_token from a secret instead. Either way, the token lives in the agent's process, so tools=[] matters: the model has no shell or file tool to read its own environment.

4. The endpoint, with fail-fast and resume

Condensed from the cookbook's server.py. Two additions come from your module 04: the tenant key and the MCP status check at init.

SESSION_ID_RE = re.compile(r"^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$")

@app.post("/sessions/{session_id}/messages")
async def post_message(session_id: str, body: MessageIn,
                       x_tenant: str = Header(), x_mcp_token: str = Header()):
    # The gateway sets these headers. A network policy guarantees only the gateway can reach us.
    if not (SESSION_ID_RE.fullmatch(session_id) and SESSION_ID_RE.fullmatch(x_tenant)):
        raise HTTPException(400, "invalid id")      # ids become file paths: this is a security check
    key = f"{x_tenant}:{session_id}"
    options = build_options(tenant=x_tenant, mcp_token=x_mcp_token, resume=_session_map.get(key))
    return EventSourceResponse(_stream_turn(key, body.prompt, options))


async def _stream_turn(key, prompt, options):
    try:
        async for msg in query(prompt=prompt, options=options):
            if isinstance(msg, SystemMessage) and msg.subtype == "init":
                bad = [s for s in msg.data.get("mcp_servers", [])
                       if s.get("status") not in ("connected", "pending")]
                if bad:                              # 401 or unreachable: say so now
                    yield ServerSentEvent(event="error", data=json.dumps({"message": f"MCP down: {bad}"}))
                    return
            yield ServerSentEvent(event="message", data=_serialize(msg))
            if isinstance(msg, ResultMessage):
                await _remember(key, msg.session_id)  # learn the SDK id for the next turn
                record_cost(key, msg)                 # lesson 5
        yield ServerSentEvent(event="done", data="")
    except Exception as exc:
        yield ServerSentEvent(event="error", data=json.dumps({"message": str(exc)}))

Why a session map? The SDK generates its own session IDs, and your callers use their own IDs. The cookbook stores the mapping in a small JSON file under CLAUDE_CONFIG_DIR, so it survives restarts with the transcripts. Two notes:

  • The cookbook's JSON file allows a race: two concurrent first turns on one ID both create sessions. Its Kubernetes tier fixes this with Redis SET NX. Use Redis or your database for the map in production.
  • Current SDK versions accept session_id= (a UUID) on the first turn. You can derive it with uuid5(namespace, key), so the ID is predictable and the map only records "this session exists". The cookbook pins SDK 0.1.50, which predates this.

5. Make sessions survive the container

OptionHowLimit
Volume at /dataCompose bind mount, Modal Volume or a Kubernetes PVC, with CLAUDE_CONFIG_DIR=/dataTies a session to one volume, often in one zone. Concurrent writers on a network volume can lose writes.
SessionStoreClaudeAgentOptions(session_store=MyStore()). Implement append(key, entries) and load(key) against S3, Redis or Postgres.Mirrors transcripts only. CLAUDE.md and cwd files need their own storage.

Three facts about SessionStore to know before you rely on it:

  • It is a mirror. The subprocess writes to local disk first, and the SDK forwards batches to your store. A run resumed from the store deletes its local copy at the end, so after that the store holds the only durable copy.
  • Writes are best-effort. A failed batch is retried, then dropped, and the stream yields a mirror_error system message. Alert on it.
  • Retention is your job. The SDK never deletes from your store unless you ask it to. Add a TTL or a lifecycle rule that matches your data policy.

6. The container

The cookbook Dockerfile installs Node.js and the Claude Code CLI with npm, pinned to match SDK 0.1.50. Current SDK packages bundle the native claude binary, so a Python image is enough:

FROM python:3.12-slim
RUN useradd -m -u 1000 agent && mkdir -p /data && chown agent /data
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # pin claude-agent-sdk: it pins the CLI too
COPY agent_service.py .
ENV CLAUDE_CONFIG_DIR=/data PYTHONUNBUFFERED=1
USER agent
EXPOSE 8000
CMD ["uvicorn", "agent_service:app", "--host", "0.0.0.0", "--port", "8000"]
  • Pin the SDK version. The bundled CLI follows the SDK version. Take patch releases. Read the changelog before a minor bump.
  • Build for the target architecture. An arm64 image from your Mac fails on an amd64 node with "failed to start Claude Code". Use docker build --platform linux/amd64.
  • Keep secrets out of the image. A .dockerignore excludes .env. The key arrives at runtime from a secret manager.

7. Size it

Start at 1 GiB RAM, 1 CPU and 5 GiB disk per concurrent session. Memory grows with session length and tool activity, so measure the peak RSS of a realistic long session, then:

agents per host = (host RAM - overhead) / (per-session RAM ceiling)

For long-running containers behind a load balancer, pin each session to one container with consistent hashing on the session ID. A pinned session keeps reaching the same live subprocess.

Try it

  1. Clone the cookbook and run tier 1: cd claude_agent_sdk/hosting/docker && docker compose up --build.
  2. Send two turns to /sessions/demo-1/messages with curl -N. Stop the container, start it, and send a third turn. The agent still remembers, because ./sessions persisted /data.
  3. In hosting/server.py, add your module 04 server to _build_options as an HTTP MCP server (host.docker.internal:8765) and change ALLOWED_TOOLS to ["mcp__research__*"]. You now have the core of the merged module.

Check yourself

Why does the cookbook's hosted server drop the Read tool that its notebook agent had?In the container, Read can reach only the container itself: other sessions' transcripts in /data and /proc/self/environ with the API key. A prompt-injected web result could steer the agent to read and leak them.
A user says "the agent forgot our conversation" after a deploy. Name two likely causes./data was not persisted (no volume or store), or the session cwd changed between versions, so resume looked in a different transcript directory and started fresh.
Why validate session_id with a regex?It flows into the session map and into filesystem paths. A value like ../../ would be a path traversal. The check is a security control.
What happens when a session hits max_budget_usd?The query stops with an error_max_budget_usd result. The result's total_cost_usd includes the response that crossed the budget.

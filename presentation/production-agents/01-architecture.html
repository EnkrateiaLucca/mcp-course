Lesson 1: The architecture

Goal: you can draw the production system from memory, name where every piece of state lives, and pick a session pattern for a given workload.

TL;DR

The problem: Your agent works on your laptop, but "putting it online" is not one job. It is two jobs, and they need opposite kinds of hosting.

The shape of the solution:

  • The agent remembers the conversation. It is a program that keeps running and keeps notes on disk. Host it like a worker that stays alive, and save its notes somewhere safe.
  • The MCP server (your tools) remembers nothing between requests. Host it like any simple website: copy it as many times as you want.
  • Before you build, choose how long each agent stays alive: one task and gone, always on, or asleep between visits and woken with its notes.

Think of it like: The agent is a chef who remembers your order. The MCP server is the kitchen tools. You can buy more knives anytime. You can't swap the chef mid-meal without handing over the notes.

1. The SDK is not an HTTP client

When your code calls query(), the Agent SDK starts a separate claude CLI process and talks to it over stdio. The Python and TypeScript SDKs bundle that binary, so the container needs no Node.js install. The subprocess does the real work:

your FastAPI handler └─ query(prompt, options) └─ spawns: claude (one process per session) ├─ owns a shell and a working directory (cwd) ├─ writes JSONL transcripts to ~/.claude/projects/ (or $CLAUDE_CONFIG_DIR/projects/) ├─ connects to your MCP servers (stdio or HTTP) └─ calls api.anthropic.com over HTTPS

Three consequences follow, and they drive every later lesson:

  1. One session = one process. N concurrent sessions need N processes. RAM per host limits concurrency.
  2. State lives on local disk. A container restart, a scale-down or a move to another node deletes it.
  3. The process does not listen on the network. Your application exposes the HTTP port and calls the SDK internally.

3. Why the MCP server can be stateless

Spec revision 2026-07-28 changed Streamable HTTP in two ways that matter for deployment:

  • No protocol sessions. The Mcp-Session-Id handshake is gone. The client sends every JSON-RPC message as its own POST to one endpoint, for example https://research.example.com/mcp.
  • No GET stream. The server answers each request with JSON or with an SSE stream scoped to that one request. Server-to-client requests (sampling, elicitation) travel inside results as "input required" results (MRTR).
  • Routing headers. Clients send MCP-Protocol-Version, Mcp-Method (for example tools/call) and Mcp-Name (for example research_topic) on every POST. A gateway or load balancer can route, rate-limit and log by tool name without parsing the body.

Result: any replica can answer any request. Your module 05 server already runs this way with stateless_http=True, json_response=True. Keep those flags: the v2 SDK still accepts older 2025-11-25 clients, and the flags keep those clients stateless too.

4. Decision 0: do you need to host the agent loop at all?

The hosting docs name an alternative first. With Managed Agents, Anthropic hosts the agent loop. Your application sends events and receives streamed results through the client SDKs or REST API. Tools run in an Anthropic-managed sandbox or in a self-hosted sandbox.

ChooseWhen
Managed AgentsYou want the agent loop as a service. You have no need to control the container, the network path or the session storage.
Self-host the Agent SDK (this class)Regulated data, an existing platform team, custom networking, per-tenant isolation you must prove, or MCP servers inside a private network.

Your custom MCP server deploys the same way in both cases. Only deployable A changes.

5. Decision 1: pick a session pattern

A session pattern says how long a container lives relative to the sessions it serves.

PatternContainer lifetimeFitsResearch assistant example
EphemeralOne container per task. It exits when the task ends.One-shot jobs: extraction, translation, a bug fix"Write a brief on X" from a queue or a cron job. The cookbook's run_once.py.
Long-runningPersistent containers. Each holds many live sessions.High-volume chat, email triage, Slack botsA team Slack bot that answers research questions all day
HybridEphemeral containers that load the transcript on start and save it backSessions with long idle gaps"Research X." Two hours later: "Now compare it with Y." The cookbook's server.py + a volume.
Multi-agentSeveral SDK processes in one containerAgents that collaborate in a shared environmentResearcher + fact-checker sharing a workspace (your module 06 composition demo)
Default for this class: hybrid. It is the most common real shape for an assistant, and it forces you to solve persistence. A hybrid container without persistence loses the transcript at shutdown, so the store is required in this pattern.

6. One request, end to end

  1. The user's app sends POST /sessions/alice-42/messages {"prompt": "..."} with a user token.
  2. The gateway validates the token, finds tenant alice, checks that alice owns session alice-42, and forwards the request to an agent container.
  3. The agent service looks up the SDK session ID for alice-42, builds ClaudeAgentOptions with resume= that ID and a per-user MCP token, and calls query().
  4. The claude subprocess reloads the transcript, calls the model, and decides to call mcp__research__research_topic.
  5. The subprocess POSTs tools/call to the MCP server with Authorization: Bearer <alice's token>. The server verifies the token, runs the tool, saves the brief under alice/ in object storage, and returns structured JSON.
  6. The agent service streams every SDK message to the user as SSE events, records the cost from the ResultMessage, and saves the session ID mapping.

Try it

Run your module 04 agent twice in a row with a follow-up question. The second run has no memory of the first. Name the two missing pieces that would fix it. (Answer in lesson 3: a stable session map and resume=.)

Check yourself

Why can't you run the agent service on Vercel functions the way you run the MCP server?Each session is a long-lived subprocess that writes transcripts to local disk. A serverless function has an ephemeral filesystem, short time limits and no process that outlives the request. The MCP server holds no session state, so serverless suits it.
A container restarts. What does the user lose if you did nothing special?The transcripts, any CLAUDE.md memory and any files in the session cwd. The next message starts a fresh conversation.
What do the Mcp-Method and Mcp-Name headers let your infrastructure do?Route, rate-limit, authorize and log per method and per tool at the gateway, without parsing the JSON-RPC body.
Which session pattern fits "process 10,000 invoices overnight"?Ephemeral: one container per task, no conversation to resume.

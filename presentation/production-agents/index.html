Agents with custom MCP servers, in production

A practical class in six lessons. One use case all the way through: the research assistant from your MCP course. Python, Claude Agent SDK 0.2.x, mcp SDK 2.3, MCP spec 2026-07-28.

The one idea that organizes everything

A production agent with a custom MCP server is two deployables, and they have opposite shapes.

user / your app │ HTTPS + user identity ▼ ┌──────────── gateway ────────────┐ authenticates the user, owns session→tenant mapping └───────────────┬─────────────────┘ ▼ ┌──── DEPLOYABLE A: agent service (container) ─────┐ │ FastAPI /health /sessions/{id}/messages (SSE) │ │ Agent SDK query() ──stdio──► claude subprocess │──HTTPS──► api.anthropic.com │ STATEFUL: transcripts, cwd, memory on disk │ └──────────────────────────┬───────────────────────┘ │ MCP over Streamable HTTP + bearer/OAuth token ▼ ┌──── DEPLOYABLE B: MCP server (your tools) ───────┐ │ MCPServer.streamable_http_app() /mcp │──► search API, DB, object store │ STATELESS: any replica answers any request │ (credentials live HERE) └──────────────────────────────────────────────────┘
  • The agent service is stateful. The SDK spawns a claude CLI subprocess per session. That process owns a shell, a working directory and JSONL transcripts on local disk. You host it like a long-lived worker, not like a stateless API.
  • The MCP server is stateless. Spec 2026-07-28 removed protocol-level sessions from Streamable HTTP. Every JSON-RPC message is its own POST. You host it like any web API: serverless, autoscaled, behind a load balancer.

Your current module 05 deploys B. Nothing in the course deploys A yet. That gap is why the demos feel like "basic stuff".

Lessons

  1. The architecture: the subprocess model, where state lives, and how to choose a session pattern.
  2. The MCP server in production: stateless HTTP, Host/Origin pinning, state off local disk, the auth ladder up to OAuth, SSRF guards.
  3. The agent service: the cookbook's HTTP + SSE contract, locked-down ClaudeAgentOptions, per-user MCP tokens, session persistence, the Dockerfile.
  4. Security: the threat model for a research agent that reads the open web, container hardening, egress allowlists, the credential proxy.
  5. Cost and observability: reading SDK cost fields correctly, budget caps, OpenTelemetry, telemetry versus evals.
  6. Ship it: Docker → Modal → Kubernetes, smoke tests, the production checklist, troubleshooting, and a blueprint for the merged module 04.

How to use these lessons

  • Read one lesson, then answer the "Check yourself" questions before you open the answers.
  • Each lesson ends with a "Try it" task you can run against the existing demos. You do not need the merged folder to do them.
  • Lesson 6 has the proposed layout for the merged module 04. Treat it as a plan to review, not as built code.

Lesson 5: Cost and observability

Goal: you can read the SDK's cost fields without double-counting, cap spend per session, export traces, and say what telemetry can and cannot tell you.

TL;DR

The problem: The AI tokens cost far more than the servers. The SDK gives you cost numbers, but they are estimates and easy to count twice.

The shape of the solution:

  • Read the cost once per turn, from the final result message. For a resumed conversation, the newest number already includes the old ones, so don't add them up.
  • Set caps per turn, per conversation and per user per day, so a looping agent can't burn money.
  • Turn on tracing so you can see which tools ran, how long they took, and where things stalled.
  • Remember: "it ran" is not "it was right". Keep running your evals against the deployed version.

Think of it like: A taxi meter shows the running total. Write down the final fare, not every reading on the way, and set a maximum before you get in.

1. Where the money goes

The hosting docs give the ratio: a minimal container costs about $0.05 per hour, and one long agent session can spend dollars in tokens. Token cost usually beats infrastructure cost by an order of magnitude or more. Optimize tokens first: fewer turns (intent-grouped tools), smaller tool results, prompt caching, and the right model per job.

2. Four scopes, one rule each

ScopeWhat it isRule
StepOne model request/response inside a query()Parallel tool calls produce several AssistantMessages with the same message_id and the same usage. Count each ID once.
query() callEverything from prompt to ResultMessageRead total_cost_usd from the ResultMessage, on success and on error subtypes. In Python it can be None.
SessionCalls linked by resumeA resumed call's result already includes the session's earlier spend. Read the latest result. Do not sum them.
Tenant / dayYour billing viewAdd the per-call deltas you recorded. Reconcile against the Usage and Cost API.

The traps

  • total_cost_usd is an estimate. The SDK computes it from a price table bundled at build time. It drifts when prices change or the SDK does not know a model. Never bill users or trigger financial decisions from it. Use the Usage and Cost API or the Console for authoritative numbers.
  • Per-step output_tokens is a placeholder. It holds the count from the start of the response. Read output tokens from the ResultMessage.
  • usage excludes subagents. total_cost_usd and model_usage include them. Use model_usage for whole-tree token accounting and a per-model breakdown.
  • Crashes can zero the totals. An error_during_execution result after a crash may carry zeroed cost fields. In streaming mode, fall back to the previous turn's result.

3. Record cost per turn, per session, per tenant

This replaces ExecutionTracker.print_summary(). It turns cumulative session totals into per-turn deltas, so a dashboard can sum them safely.

_last_total: dict[str, float] = {}      # session key -> last cumulative total (use Redis in prod)

def record_cost(key: str, msg: ResultMessage) -> None:
    total = msg.total_cost_usd or 0.0
    delta = max(total - _last_total.get(key, 0.0), 0.0)   # resumed results include earlier spend
    _last_total[key] = total
    log.info(json.dumps({
        "event": "agent_turn",
        "tenant": key.split(":", 1)[0], "session": key,
        "subtype": msg.subtype,                     # success | error_max_turns | error_max_budget_usd | ...
        "turn_cost_usd_est": round(delta, 6),
        "session_cost_usd_est": round(total, 6),
        "num_turns": msg.num_turns, "duration_ms": msg.duration_ms,
        "models": list((msg.model_usage or {}).keys()),
    }))

One JSON line per turn is enough to answer: cost per tenant per day, sessions that hit the budget, and turns that end in errors.

4. Cap spend before it happens

GuardSet withWhat happens
Turn capmax_turns=12The query stops with error_max_turns and raises after it yields the result. Catch it.
Dollar cap per callmax_budget_usd=0.50Stops with error_max_budget_usd. Counts only this call's spend, not spend restored from a resumed session.
Daily cap per tenantYour code: sum of turn_cost_usd_estThe gateway refuses new turns once a tenant reaches its limit.
Subagent fan-outmaxTurns in each AgentDefinitionBounds each subagent. Large parallel fan-outs can also hit rate limits: dispatch in smaller batches.

Because max_budget_usd ignores restored spend, a long conversation can exceed it across many calls. The per-tenant daily cap closes that gap.

Prompt caching

The SDK caches automatically. Watch cache_creation_input_tokens (written at a higher rate) and cache_read_input_tokens (read at a reduced rate) in the usage. With API-key auth the cache TTL defaults to 5 minutes. A hybrid assistant whose users come back after 20 minutes pays full input price on every return. ENABLE_PROMPT_CACHING_1H=1 requests a 1-hour TTL: writes cost more, and more reads hit the cache. Measure both before you keep it.

5. Traces, metrics and logs with OpenTelemetry

The SDK reads OTEL settings from the environment. Set them on the container, and every query() exports:

CLAUDE_CODE_ENABLE_TELEMETRY=1
CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1      # needed for traces only
OTEL_TRACES_EXPORTER=otlp
OTEL_METRICS_EXPORTER=otlp
OTEL_LOGS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4318
  • Prompt text and tool inputs are not exported by default. Keep it that way unless your data policy allows otherwise.
  • Traces show which tools ran, how long each took, and where a session stalled. That is the question ExecutionTracker tried to answer for one run.
  • Add the MCP server's own request logs (method, tool name, subject, latency) and you can follow one turn across both deployables.

Alerts worth having on day one

  • mirror_error system messages (transcripts not reaching your store)
  • Rate of error_max_budget_usd and error_max_turns results per hour
  • MCP server status other than connected at init
  • Peak RSS per session approaching your per-session memory ceiling

6. Telemetry is not correctness

Everything above tells you the agent ran: cost, time, tools, errors. None of it tells you the brief was right. Your module 04 evals.py answers that: deterministic checks, then an LLM judge, then a CI gate. In production, run the same evals against the staging deployment through the real HTTP contract, not against a local script. A deploy that breaks the MCP URL, the auth or the model ID then fails the gate before users see it.

Try it

  1. Run module 04's agent with a prompt that makes it call research_topic twice in parallel. Print every AssistantMessage.message_id and its usage. Find the duplicate IDs.
  2. Set max_budget_usd=0.01 and run a research prompt. Read the result's subtype, and compare usage with total_cost_usd.
  3. Resume the same session for a second call. Confirm that the second total_cost_usd includes the first.

Check yourself

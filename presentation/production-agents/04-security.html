Lesson 4: Security

Goal: you can explain why a research agent is a high-risk agent, and you can place each control (gateway, tool scope, container, egress proxy, credential proxy) on the system diagram.

TL;DR

The problem: A research agent reads random web pages, holds private data, and can talk to the internet. Those three together let a malicious page trick it into leaking data.

The shape of the solution:

  • You can't stop every trick. So shrink what a tricked agent can do.
  • Check who the user is before anything reaches the agent, and make sure each user only sees their own conversations.
  • Box the agent in: no extra tools, not run as admin, no unneeded permissions.
  • Cut its internet: it may only talk to the AI model and your tools server. Keep passwords outside the box and add them on the way out.

Think of it like: Let a new hire read any mail, but give them a phone that can only call two numbers. Even a scam letter can't get them to call the scammer.

1. The threat model, applied to this agent

An agent's actions depend on the content it reads. Instructions hidden in a file, a web page or a tool description can steer it (prompt injection). Model error can also cause harm without any attacker. The secure-deployment guide does not try to filter that out. It limits what a steered agent can reach.

Check the research assistant against the "lethal trifecta":

IngredientPresent?Where
Untrusted contentYesresearch_topic fetches arbitrary web pages and puts excerpts in the context
Private dataYesOther users' briefs, transcripts in /data, the API key and MCP token in the environment
A way to send data outYes, by defaultAny outbound network path: a fetch, a tool argument that reaches the internet, a DNS lookup

All three are present. So this agent needs every layer below. The aim is to remove the third ingredient, because you cannot remove the first two without removing the product.

3. A hardened container

From the secure-deployment guide. Each flag removes one capability the agent never needs:

docker run \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=100m \
  --network none \
  --memory 2g --cpus 2 --pids-limit 100 \
  --user 1000:1000 \
  -v agent-data:/data \
  -v /var/run/proxy.sock:/var/run/proxy.sock:ro \
  research-agent
FlagEffect
--cap-drop ALL, no-new-privilegesNo Linux capabilities, no setuid escalation
--read-only + --tmpfsImmutable root filesystem; scratch space is cleared at stop
--network noneNo network interface at all. The only way out is the mounted Unix socket to a proxy on the host.
--memory, --pids-limitCaps resource exhaustion
--user 1000:1000Not root

Pick the isolation strength from the threat model:

TechnologyIsolationOverheadUse when
sandbox-runtimeGoodVery lowOne developer, CI jobs. No Docker needed.
Docker (hardened as above)Depends on setupLowSingle-tenant services
gVisor (--runtime=runsc)ExcellentMedium to high; file-heavy work is much slowerMulti-tenant, untrusted content
Firecracker / VMsExcellentHighStrict tenant separation, regulated data

A research agent with tools=[] does little file I/O beyond its transcripts, so gVisor's file-I/O penalty costs little here. Measure it on your workload before you commit. For a multi-tenant deployment, it is a reasonable default.

4. Egress: the control that holds when the others fail

Deny all outbound traffic, then allow a short list. For this agent the list has two entries:

api.anthropic.com:443              # the model
research-mcp.internal:443          # your MCP server (or its public host)

Everything else, including the web pages the research tool fetches, leaves from the MCP server, not from the agent container. That split is deliberate. The agent never needs the open internet. The MCP server needs it, and it applies its own SSRF rules.

How the cookbook's Kubernetes tier enforces it:

  • A NetworkPolicy lets agent pods reach only the egress proxy (443) and DNS (53).
  • The egress proxy (nginx) terminates TLS from the agent and re-encrypts to api.anthropic.com.
  • The policy works only if the cluster's CNI enforces it (Calico, Cilium, GKE Dataplane V2). kind's default CNI does not, so the quickstart installs Calico.
  • Known gap the cookbook documents: port 53 stays open, so DNS tunneling remains a residual channel.

Prove it from inside a running agent pod. This should fail:

kubectl -n claude-agent exec "$AGENT_POD" -- python3 -c \
  "import socket; socket.setdefaulttimeout(5); socket.create_connection(('example.com',443)); print('REACHED')"

5. Credentials: inject them outside the boundary

The recommended pattern: a proxy outside the agent's container adds the credential to each request. The agent makes the call but never holds the secret.

CredentialPattern
Anthropic API keySet ANTHROPIC_BASE_URL=http://proxy:8080. The SDK sends model requests to the proxy in plain HTTP, and the proxy adds the key and forwards. Envoy's credential_injector or LiteLLM can do this.
Search API key, database passwordKeep them in the MCP server (lesson 2). The agent calls a tool; the server makes the authenticated request.
MCP tokenPer user, short-lived, audience-bound to the MCP server (lesson 3). If it leaks, it opens only that user's tools, and only until it expires.

One trap: HTTPS_PROXY gives the proxy only an opaque TLS tunnel. A proxy can inject headers into HTTPS traffic only if it terminates TLS and the agent trusts its CA certificate. ANTHROPIC_BASE_URL avoids that for model calls.

6. Never put these in the image or a mount

.env files, ~/.aws/credentials, ~/.config/gcloud/, ~/.kube/config, ~/.docker/config.json, ~/.git-credentials, .npmrc, .pypirc, *.pem, *.key, *-service-account.json. A read-only mount still exposes them.

Try it

  1. Run your module 06 attack_demo.py. Then ask: with the lesson 3 options (tools=[], MCP-only allowlist), which step of the attack still works? Which layer would stop the rest?
  2. Run the cookbook's Kubernetes quickstart and the example.com test above. Then call the gateway with Bob's token on Alice's session and confirm the 403.

Check yourself

Which ingredient of the lethal trifecta can you remove without breaking the research product?The exfiltration path. The agent container needs only the model API and the MCP server. Web fetching happens inside the MCP server, which applies its own rules.
Why is --network none plus a Unix socket stronger than an allowlist inside the container?The container has no network interface to misuse. All traffic must pass through a proxy that runs outside the agent's boundary, where a compromised agent cannot change the rules.
Why can't a plain HTTPS_PROXY inject an API key?The proxy sees only an encrypted CONNECT tunnel. It must terminate TLS, with its CA trusted by the agent, to modify the request.
The gateway authenticates Alice. What second check must it make on every request?That the session_id belongs to Alice. Authentication without session ownership lets any user read any session.

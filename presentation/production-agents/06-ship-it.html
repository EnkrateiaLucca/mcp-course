Lesson 6: Ship it

Goal: you can deploy both pieces at three levels of rigor, prove each deployment works with smoke tests, and review a plan for the merged module 04.

TL;DR

The problem: You know what to build. Now you need to put it online step by step and prove each step works.

The shape of the solution:

  • Same box, three homes: first Docker on your laptop, then a shared cloud sandbox (Modal), then a full cluster (Kubernetes) where each conversation gets its own box.
  • Test after every deploy: does it answer, does it remember after a restart, does it reject strangers, does it stop at the budget.
  • Use the checklist and the troubleshooting table when something breaks.
  • The merge plan: one new module 04 with a mcp_server/ folder and an agent_service/ folder, run together with one compose file.

Think of it like: A test kitchen at home, then a food truck, then a restaurant chain. The recipe never changes. Only the building around it gets bigger.

1. Three tiers, one image

The cookbook's main lesson: the agent image and its HTTP contract stay the same from your laptop to Kubernetes. Only the machinery around them changes.

2. Tier 1: both deployables in one compose file

services:
  research-mcp:
    build: ./mcp_server
    environment:
      MCP_AUTH_TOKEN: ${MCP_AUTH_TOKEN}
      PUBLIC_HOST: research-mcp:8000      # the Host header the agent sends (lesson 2 pinning)
    # no "ports": only the agent can reach it

  agent:
    build: ./agent_service
    env_file: .env                        # ANTHROPIC_API_KEY, MCP_AUTH_TOKEN
    environment:
      RESEARCH_MCP_URL: http://research-mcp:8000/mcp
      MODEL: claude-sonnet-5
      MAX_BUDGET_USD: "0.50"
    ports: ["127.0.0.1:8000:8000"]        # loopback only: there is no gateway in tier 1
    volumes: ["./sessions:/data"]
    depends_on: [research-mcp]

Tier 1 has no gateway, so you send the gateway's headers yourself with curl. That is acceptable only because the port is bound to loopback.

3. Tier 2: Modal + a public MCP server

# MCP server: module 05 flow, with lesson 2 changes
vercel deploy --prod
uv run test_client.py https://<app>.vercel.app/mcp

# Agent: the cookbook's driver creates a Sandbox from the same Dockerfile
python hosting/modal/modal_app.py      # prints the URL and a random AGENT_AUTH_TOKEN

The Modal URL is public, and the token is the only lock. The cookbook prints a warning for this reason: do not share the URL and the token together. Modal Volumes use explicit commits. With many concurrent sandboxes writing sessions, move to a SessionStore.

4. Tier 3: Kubernetes, pod per session

cd claude_agent_sdk/hosting/kubernetes
export ANTHROPIC_API_KEY=sk-ant-...
./kind-quickstart.sh                    # builds 3 images, installs Calico, prints ALICE_TOKEN / BOB_TOKEN

What the gateway does for you: creates and deletes agent pods, routes /sessions/{id}/messages to the right pod, records the owning tenant in Redis and returns 403 to anyone else, and keeps a standby pool warm (pods take 10–30 s to start).

Two additions for our system:

  1. Deploy the research MCP server as a Deployment + Service in the namespace.
  2. Allow agent pods to reach that Service in network-policy.yaml. The cookbook policy allows only the egress proxy and DNS, so without this change every MCP call fails, and the init status check from lesson 3 reports it.

What tier 3 still does not give you, by the cookbook's own list: a real identity provider, durable session storage after a pod is reaped, gateway autoscaling, DNS-level egress control, and hardened supporting services.

6. Production checklist

MCP server

  • ☐ stateless_http=True; Host/Origin pinned with protection on
  • ☐ Auth: constant-time bearer, or OAuth with token_verifier + audience check
  • ☐ Tenant read from the token; storage keyed by tenant; no local-disk state
  • ☐ Third-party credentials held by the server; SSRF guard on every fetch and redirect
  • ☐ Request size and duration limits set; logs with method, tool, subject and latency

Agent service

  • ☐ Behind a gateway that authenticates users and checks session ownership
  • ☐ tools=[], strict_mcp_config=True, allowed_tools=["mcp__research__*"], setting_sources=[]
  • ☐ Per-tenant cwd and CLAUDE_CONFIG_DIR; CLAUDE_CODE_DISABLE_AUTO_MEMORY=1
  • ☐ max_turns, max_budget_usd, and a per-tenant daily cap
  • ☐ Sessions persisted (volume or SessionStore); alert on mirror_error
  • ☐ SDK version pinned; image built for the node architecture; non-root user
  • ☐ Egress: Anthropic API + MCP server only; API key via secret manager or ANTHROPIC_BASE_URL proxy
  • ☐ OTEL exported; cost records per turn; evals gate the deploy

7. Troubleshooting

SymptomLikely causeFix
"Claude Code not found" at service startThe service runs with a different PATH or install than your shellInstall the SDK in the image's Python; do not rely on a host CLI
"Failed to start Claude Code"Binary built for another architecture or libc, or it lost its execute bit--platform linux/amd64; use a glibc base image such as python:3.12-slim
421 through the tunnel or the platformThe public hostname is not in allowed_hostsAdd it (lesson 2). Do not turn the protection off.
401 from the MCP serverToken mismatch, expired token, or wrong audienceCheck the init status line; check the token's aud
Resume starts a new conversation without an errorThe cwd or CLAUDE_CONFIG_DIR changed, or /data was not persistedKeep cwd stable per tenant; mount /data or use a SessionStore
Memory climbs on long sessionsExpected growth with session lengthCap session length; recycle subprocesses; re-measure the per-session ceiling
Rate-limit errors during subagent workA wide parallel fan-outDispatch subagents in smaller batches

Check yourself

Which piece stays identical across all three tiers?The agent image and its HTTP contract. Volumes, auth, routing and network policy change around it.
You deploy to tier 3, and every research call fails while the model API works. First suspect?The NetworkPolicy. Agent pods may reach only the egress proxy and DNS, so they cannot reach the MCP server Service until you allow it.
Why is smoke test 4 (restart, then continue) the most important one for a hybrid assistant?It is the only test that proves persistence. Without it, the first rolling deploy wipes every user's conversation.
